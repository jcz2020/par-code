# v0.8.0 真机全面测试报告（2026-11-02）

环境：安装版 `par 0.8.0 (built on PAR SDK v0.12.0-beta.20261023)`，配置的真实 provider（模型不在 PAR 的静态窗口表内），tmux 真 PTY，scratch workspace `/root/dev/PAR-CODE/.omo/audit-ws`。
项目基线：`dune build && dune runtest` exit 0。

## 结论

核心链路（问答 / 工具 / 计划 / 目标 / 记忆 / 会话恢复）能跑，但有 **4 个 P0** 会在日常使用中直接打断会话，其中两个会让会话永久不可用。v0.8.0 不建议作为稳定版继续使用，建议出 v0.8.1 修 P0。

## P0（阻断使用）

### P0-1 上下文压缩在 ~6.4k token 静默截断，制造孤立 tool result，provider 400 + 会话永久损坏

**复现 A（长会话）**：普通 build 回合（36 条消息 / 8171 tokens）后，max mode 3 个候选全失败，fallback 也失败：
`Invalid input: ... invalid params, tool result's tool id(call_yt61...) not found (2013)`。
**复现 B（新会话）**：新会话 → `/max on` → 一个 max 问题（context 5802） → `/max off` → 一条普通小指令 → 立刻 400(2013)。

**证据**：
- `events` 表 `Context_compressed`：`tokens_before 8171 → tokens_after 3408`，`messages_before 36 → messages_after 13`，`strategy_used ["Summarize",{"max_tokens":8000,"summary_model":null}]`（7 次）。
- 落库会话 `71962b30` 只剩 13 条，开头 `System,Tool,Tool,...`（两条 write 结果失去 assistant tool_call）；`52bbeb7a` 有 84 条消息、19 条孤立 tool result。
- payload dump：`/tmp/par_audit_evidence/max-mode-orphan-payload.json`、`second-400-after-max.json`。

**根因**：
1. `Par.Context_manager.default_context_window` 对未知模型返回 **8000**；本次使用的模型不在静态表。
2. par-code `make_llm_service` 设 `context_window_fn = None`，agent 也未设 `context_window_override`（`lib/par_code_setup.ml:106,132`）。
3. agent 默认 `context_strategy = Some (Summarize {summary_model=None})`；SDK `apply_summarize` 因 `summary_model=None` 直接 `apply_truncate_oldest`，**不剥离孤立 tool result**（`/root/dev/PAR-0.12.0-beta/lib/core/context_manager.ml:118-133`）。
4. par-code 在 `Error (e, recovered_conv)` 把 `recovered_conv` 覆盖落库（`lib/par_code_repl.ml:452`），截断变持久损坏。

**修复方向**：配置真实 `context_window_override`（或实现 `context_window_fn`）；agent 传 `~context_strategy:None`（让 SDK 用主模型摘要）或传带 summary_model 的策略；Error 分支不要无条件覆盖当前会话，至少剥离孤立 Tool 后落库；上游 PAR 应在 truncate 后剥离孤立 tool result。

### P0-2 默认配置下 recall_memory 卡 130 秒，Ctrl+C 无法中断

planner 调 `recall_memory` → `✓ (130768.2ms)`；第二次继续卡。Ctrl+C 只显示 `[cancelling — Ctrl+C again to force exit]`，40s 仍未退出，第二次强杀。把 `embedding_base_url` 指到 `127.0.0.1:9` 后同一查询 **65.1ms** 返回 5 条。

**根因**：`lib/par_code_setup.ml:214-222` 对所有支持 embeddings 的 provider 无条件构造 `memory_embedding_fn = Some(...)`，即使 `embedding_model=None`；SDK `resolve_mode` 有 embedding 即默认 Hybrid，每次 recall 先调外部 embedding 端点，超时后才回落 FTS。

**修复方向**：仅当 `embedding_model` 非空且 base_url 配置时才传 embedding_fn；或默认 Keyword_only；给 embed 调用加短超时。

### P0-3 一次 malformed tool call（arguments=null）永久毒化会话

**复现**：新会话发一条普通指令；模型某次 `bash` tool call 的 `arguments` 为 `null`（payload 可见）；下一请求 provider 直接 400 `invalid params, 400 (2013)`。之后连 `你好` 都失败。`/reset` 可恢复（但错误提示不会告诉用户）。

**证据**：`/tmp/par_audit_evidence/fresh-session-400.json` 第 11 条 `{"name":"bash","arguments":null}`；随后同一会话每轮 400。

**根因**：SDK 把 `null` arguments 原样存入历史并在后续请求重发；provider 校验失败。par-code 的 v0.7.4 只清理孤立 tool result，未处理 null/malformed arguments。

**修复方向**：invoke 前/落库前规范化 `tool_calls[].arguments`（null→`{}`，非对象→`{}`）；错误恢复时同样清洗；上游 PAR 最好在请求组装层做。

### P0-4 doom-loop 把“失败的编辑”当“重复编辑”，6 次后中止整轮（无 goal 也报 goal aborted）

普通 build 回合让模型 `apply_patch` 改 2 个文件；补丁失败 6 次后：`✗ goal aborted (doom loop) — cancelling this turn: Edit repeat signal: 6 near-duplicate edits detected`，所有在飞 tool 被 cancel，无最终回答。

**根因**：`lib/par_code_repl_io.ml` 的 `Tool_failed` 分支 `output=None`；`Par_code_doom_loop.record` 对编辑工具取 `""` → `shingle_lines "" = [""]`，任意两次失败 Jaccard=1.0，全部计入 near-duplicate；阈值 `edit_matches=2` → 6 次 Abort。`repl.ml:443-448` 又按 goal 中止处理。

**修复方向**：失败事件用错误文本作为 output（或不参与 edit-repeat 计数）；Abort 仅在 goal Active 时执行；文案区分 turn / goal。

## P1

### P1-1 每次 plan_submit 生成两个 plan 文件

`plan_submit` 已保存真实 plan（7373B `20-35-34Z.md`），随后 `repl.ml:502-512` 的 Plan→Build 自动持久化把最后一条 assistant 文本保存成第二个（957B `20-35-36Z.md`）。`par plan list` 出现重复。修复：先 `consume_submitted_plan ()`，本轮已提交则跳过自动持久化。

### P1-2 多文件 apply_patch 缺 `diff --git` 时报错误导且不可恢复

- `expected 'PAR_WRITE_OK', got 'PAR_WRITE_OK'`（字符串相同却 mismatch）
- `expected '-- a/out.txt', got end of file`
模型无法定位“每段需 `diff --git` 头”，连续重试 6 次后触发 P0-4。修复：工具描述/系统提示写明段头要求；错误信息指出段边界（上游解析器最好直接支持）。

### P1-3 max mode 无候选超时/进度，慢 provider 拖数分钟

3 候选并发，候选 3 超过 2 分钟；UI 只有 `candidate 1/3 done`、`2/3 done`；无超时/取消提示。期间 Ctrl+C 显示 cancelling，但候选 3 仍完成，selector 仍运行并开始 execute，最后才 `[cancelled by user]`。

### P1-4 `par session fork` 打印的 id 无法用于 `--continue`

`par session fork be096997` → `→ 4b182b31`，提示 `Use 'par --continue <new-id>'`；实际 `par -c 4b182b31` → `✗ No session matches prefix`。fork 也不出现在 `par session list`。
**根因**：`resolve_id` 走 `list_sessions`，后者是 `events JOIN conversations`；fork 只写 conversations、无 events，故前缀查不到。全 36 位 id 可用。
修复：fork 后写入一条事件，或 `resolve_id` 直接查 conversations 表。

### P1-5 `par session list/show` 输出非法 UTF-8

标题按字节截断（`lib/par_code_session.ml:145-151`，`String.sub result 0 50`）把 CJK 切成半个字符。实测 `par session list` stdout 第 234 字节非法；任何 UTF-8 管道/脚本解码直接抛异常，终端显示乱码。修复：按 UTF-8 边界截断（可复用 `Par_code_selector` 的安全 truncate）。

### P1-6 Ctrl+C 不能中断流式生成

在 4s 时按 Ctrl+C，回合继续 **29.5s** 直到模型把 2000 字写完，返回完整答案，没有 `[cancelled by user]`。用户以为没生效。修复：流式读取路径检查 cancellation token；或至少在 UI 上明确“正在取消，等待当前流结束”。

### P1-7 `/dev/null` 被当作“项目外路径”要求审批

goal 链里 `find ... 2>/dev/null` 触发 `outside project: /dev/null, /dev/null, /dev/null [y/a/N]`。`Par_code_approvals.classify` 把 `/dev/null` 当外部路径。修复：忽略 `/dev/null`、`/dev/stdout`、`/dev/stderr` 等特殊文件。

### P1-8 checkpoint 内容会事实错误

`/checkpoint` 生成：`decisions: ... 正文约 2000 字...; open: 尚未输出 Python GIL 技术说明正文`——但同一会话上一轮已经完整输出了该正文。resume 时会把“未完成”注入上下文。修复：checkpoint prompt/输入窗口需覆盖最近 assistant 完整回复，或要求引用证据。

## P2

- **假阳性 action-streak**：连续 4 次正常 bash 调用就 `Action streak signal: 4 consecutive other actions`（`classify_tool` 把所有非 info 工具归为 other）。建议按工具名/参数区分或排除 bash。
- **流式文本 tool 边界缺换行**：`…tests now.Now running…`、`…for 'par'.返回了…`。
- **`/cost` operational metrics 恒为 0**：`tool_invocations_total 0`、`events_published_total 0`、`tools_visible 0`，尽管实际多次 tool 调用。
- **`/checkpoint` 顺带触发记忆提取**（`[extracting memories...]`），用户未必预期；`/quit` 也同步阻塞在提取（本次约 10s，正常结束）。
- **`[migration] 0 of 33 legacy conversations backfilled`** 在 `session list/fork/show` 反复出现，且永远 0——噪声。
- **`par plan list` / `/help` / `/cost` 两列表格行间多空行**（183 列终端下明显）。
- **bash policy 拒绝算术展开**：`echo READY_$((1+1))` 被 Coder policy 拒绝（上游策略限制，记录备查）。
