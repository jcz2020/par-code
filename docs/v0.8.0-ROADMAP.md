# v0.8.0 ROADMAP — Best-of-N（max mode）

> 状态：**已发布**（v0.8.0，2026-11-02）。W0–W6 全部落地；`dune build` / `dune runtest`（24 套）与集成套件（12 个文件，含新增 max mode 4 条）全绿，并用真机 provider 走查过 answer / execute / 失败回退 / Ctrl+C / plan 模式跳过五条路径。
> 日期：2026-10-21（草案 v1）／2026-11-02（实现）
> 落地四周处的实现偏离（详见 `docs/DECISIONS.md` 2026-11-02 实现注记）：候选 agent 独立注册为 read-only 的 `max_candidate`；`answer` 路径合成 `invoke_result` 复用现有收尾逻辑；候选与本轮 invoke 共用一个取消 token；goal chain 续跑与 Plan 模式跳过 max mode。
> 前置：**[v0.7.5 ROADMAP](v0.7.5-ROADMAP.md)**（PAR SDK 0.11 跟进 + 构建可复现化）必须先落地——本里程碑要用的 `Runtime.invoke` / `Types.conversation` 语义要在新地板上重新核读一遍，且 v0.7.5 会把 CI 的 PAR pin 从分支 tip 改为 tag。

## 0. 主题与范围

**一句话**：让 agent 面对一个请求时**同时想好几条路**，自动挑出最好的那条再动手。

| 维度 | 决定 |
|---|---|
| 版本类型 | MINOR（v0.8.0），纯增量，无破坏性 API 变更 |
| 核心用户价值 | *"It tries several approaches and picks the best."*（README roadmap 行） |
| **做** | max mode 开关与配置（W0）、N 路并发候选执行器（W1）、候选选择器（W2）、REPL/CLI 接线与会话接管（W3）、成本可见（W3）、测试（W4）、文档同步（W5） |
| **不做** | ① 执行级 best-of-N（多候选并发改同一工作区）→ 推迟到 v0.9.0，见 §3 决策 4；② 替换 goal judge（目标达成判定与候选选择是两件事）；③ 候选 prompt 策略库无限扩展（固定 3 条策略种子）；④ 候选间的记忆/技能隔离（沿用同一 runtime）；⑤ **PAR SDK 版本跟进**（0.10.0 → 0.11.0-beta / 0.12 的 `apply_patch`、`register_agent_as_tool`、progressive tool loading、多模态输入）→ 建议独立 patch 版本先行（低风险、与本里程碑解耦），不占用 v0.8.0 范围 |
| 范围决策记录 | 见 §3；随本 ROADMAP 落地时同步 `docs/STRATEGY.md` roadmap 列表与 README roadmap 行 |

**为什么现在做**：README roadmap 已把 v0.8.0 定位为 Best-of-N；PAR SDK 侧并发原语已就位（`Runtime.invoke_parallel`，PAR v0.8.0 起），但**它缺的恰好是 max mode 需要的那一半**（见 §1.2）——所以 v0.8.0 的主体是 par-code 侧的编排，同时把缺口作为 PAR SDK feedback 归档。

## 1. 背景与实测证据

### 1.1 现状（par-code v0.7.3，已发布）

- REPL 单轮路径：`lib/par_code_repl.ml:515` 一次 `Runtime.invoke rt ~agent_id ~message ?conversation:!conv ~on_tool_event ~on_chunk ...`；返回的 `conversation` 直接接管 `conv` 引用并落库。
- 已有"判定"能力但用途不同：`lib/par_code_judge.ml` 的 judge agent 判定 **goal 是否达成**（JSON `{"goal_met":bool,...}`），每 3 步或 claim 时触发。
- 已有只读 agent 形态可复用：planner（`lib/par_code_setup.ml:408`）与 explore（`:466`）都只挂只读工具子集。

### 1.2 SDK 侧核读结论（决定实现路线）

| # | 核读结论 | 位置 | 对 max mode 的含义 |
|---|---|---|---|
| S1 | `Runtime.invoke_parallel` 的分支是**无状态** `Agent_call`：`Engine.run_agent` 收 prompt，产出 `{text, tool_calls}` JSON | `workflow_engine.ml:141-157` | 分支不接续父会话，不存在"候选会话"概念 |
| S2 | `parallel_invoke_result.successes : (agent_dispatch_spec * Yojson.Safe.t) list` | `runtime.mli:13-17`（main 与已装 0.10.0 一致） | 拿不到分支的 conversation → **无法接管胜出候选的会话** |
| S3 | `agent_dispatch_spec` 字段仅 `agent_id / input / workspace / approval_handler / blocking_approval` | `runtime.mli:5-11` | 没有 per-branch conversation 入口 |
| S4 | `Runtime.invoke` 的 `~update_current:false` 时**不写** `rt.current_conversation`（`Current_conversation.set` 仅在 `update_current=true` 分支执行） | `runtime.ml:1153`、`1168`、`1118` | 候选并发时能保证不动父会话 |
| S5 | `rt.current_conversation` 有 mutex 保护 | `runtime.ml:100-102` | 但语义仍是 last-writer-wins → 候选必须显式传 `~update_current:false` |
| S6 | `Runtime.invoke` 支持 `?conversation:` 传入起始会话，返回值携带新会话 | `runtime.mli:1176-1184` | 每个候选拿一份会话副本即可完全隔离 |
| S7 | `Runtime.invoke_async` **没有** `?save` / `?update_current` 参数，默认 `update_current=true` | `runtime.mli:275-289`（main 与已装 0.10.0 一致） | 直接用 `invoke_async` 并发会覆盖 `rt.current_conversation` → 不能直接用 |
| S8 | par-code 已是 `eio` / `eio_main` 直接依赖，且已用 `Eio.Fiber.fork` 做异步 checkpoint | `par_code.opam`、`lib/par_code_checkpoint.ml:426` | 候选 fan-out 由 par-code 自己编排即可，无需 SDK 新接口 |

**结论**：`invoke_parallel` 解决的是"多 agent 并行派发 + 合并 JSON"，不是"同一会话的 N 个候选"。max mode 需要后者，**par-code 侧用 `Runtime.invoke` + 会话副本 + `~update_current:false` 自己 fan-out**（Eio fiber + Semaphore + 共享取消 token）。

## 2. 用户可见行为

### 2.1 开关与入口

| 入口 | 形式 | 说明 |
|---|---|---|
| 配置 | `max_mode`（bool，默认 `false`） | 全局默认 |
| 配置 | `max_candidates`（int，默认 `3`） | 候选路数，范围 2–5 |
| REPL | `/max` | 显示当前状态（off / on, N candidates） |
| REPL | `/max on` / `/max off` | 开关 |
| REPL | `/max 4` | 开关并设路数 |
| CLI | `par --max 3` | 本次会话开启（与 `--goal` 同风格） |

### 2.2 一次 max mode 回合的可见过程

```
> add retry to the uploader

[max mode] 3 candidates running…
  candidate 1/3 · done
  candidate 2/3 · done
  candidate 3/3 · done
[max mode] selected candidate 2/3 — it verified the existing backoff helper instead of adding a new one
```

- 候选阶段**不流式输出**（N 路流会互相穿插，不可读）；每个候选只报一行状态。
- 选完后正常渲染胜出候选的最终回复；若选择器判定"需要执行"，则先渲染一行"已选定方案"，再进入正常 build 回合（流式照旧）。
- 成本按 N 路累加展示（沿用现有 `/cost` 口径）。

### 2.3 失败与回退

| 情况 | 行为 |
|---|---|
| 部分候选失败 | 用成功候选继续；失败数在状态行注明 |
| 全部候选失败 | 走现有单路 invoke（等价于关掉 max mode 跑一遍），不新增错误类型 |
| 选择器失败/无法解析 | 回退到 0 号候选，`kind=answer`（直接用 0 号候选文本作答） |
| 用户 Ctrl+C | 共享取消 token 一次性取消全部候选；已完成的候选结果丢弃，不落库 |
| goal chain 进行中 | **跳过 max mode**（自主循环里 N 倍成本不可控），并提示一次 |

## 3. 范围决策记录（R1 判定）

| # | 决策 | 判定 | 理由 / 退役条件 |
|---|---|---|---|
| 1 | max mode 由 par-code 侧 fan-out 实现（`Runtime.invoke` + 会话副本），**不用** `Runtime.invoke_parallel` | **架构正确** | S1–S3：`invoke_parallel` 分支无会话、只回 JSON，胜出候选的会话无法接管。除非 PAR 新增 conversation 级并发 API（已归档为 feedback），否则这是唯一正确路径 |
| 2 | 候选 agent **只读**（read/grep/find/ls/recall_memory/search_history/git_status/git_log），执行阶段单路 | **架构正确** | N 个候选在同一工作区并发写文件必然互相覆盖；best-of-N 的价值在"思路多样性"，不在"并发写" |
| 3 | 候选调用统一 `~update_current:false ~save:false`，胜出会话由 par-code 显式接管并落库 | **架构正确** | S4–S6：这是唯一能保证父会话不被候选污染的组合 |
| 4 | 执行级 best-of-N（每候选一个 git worktree 并发改、胜者 diff 回灌主工作区）**推迟到 v0.9.0** | **范围妥协** | 退役条件：出现"同一请求多次产出不同可运行实现、且用户明确要比较实现"的需求；触发信号：max mode 的 answer 类请求占比高但用户频繁要求"换个实现再来一版"。替代方案已明确：worktree 隔离 + `git diff` 回灌 + 脏工作区基线处理（需先解决"worktree 从 HEAD 起、看不到主工作区未提交改动"的基线问题） |
| 5 | 选择器是**独立 agent**（`selector`，tools=[]，走 `Runtime.invoke_generate`），不复用 judge | **架构正确** | judge 的 system prompt 是"goal 是否达成"专用；选择器判的是"哪个候选更好"，语义与输出 schema 都不同。独立 agent 才能换模型/换 prompt/单独调参 |
| 6 | 候选 prompt 用**策略种子**制造多样性（固定 3 条），不是同一 prompt 跑 N 遍 | **架构正确** | 同 prompt + 同温度 → 候选高度同质，N 倍 token 换不来差异 |
| 7 | max mode **默认关闭** | **架构正确** | 成本 N 倍；默认开启会静默改变所有用户的成本预期 |
| 8 | 候选阶段不流式渲染 | **架构正确** | N 路 chunk 交错不可读；候选结束一次性渲染胜者结果 |

## 4. 工作项

### W0 — 配置与入口 🔴P0

- `lib/par_code_config.ml`：`config` 记录加 `max_mode : bool`、`max_candidates : int`；默认值 `false` / `3`；`par config set` 支持这两个字段（布尔解析复用既有 `parse_bool`）；JSON 序列化加字段（**旧配置文件缺字段时用默认值兜底**，不能因为老配置反序列化失败）。
- `lib/par_code_repl.ml`：`/max` 命令（状态/开关/设路数）；`bin/cli_args.ml` + `bin/main.ml`：`--max N`。
- 越界处理：`/max 1` 或 `/max 9` → 提示范围 2–5，不改状态。

### W1 — 候选执行器 🔴P0

新模块 `lib/par_code_max_mode.ml`（+ `.mli`）：

- `run_candidates ~rt ~agent_id ~message ~conversation ~n ~candidates` → 候选结果列表。
- 实现：`Eio.Fiber.fork_promise` + `Eio.Semaphore`（上限 = n）+ **一个共享取消 token**（复用本回合已建的 `turn_token`）；每个候选调用 `Runtime.invoke rt ~agent_id ~message ~conversation:(会话副本) ~update_current:false ~save:false ~cancellation_token:token`。
- 会话副本：`Types.conversation` 是不可变记录（`types.mli:179-182`：`messages` / `metadata`），浅拷贝即可（`{ c with messages = c.messages }`）。
- 隔离要求：**不得**传 `on_chunk`（不流式）；`on_tool_event` 按候选 id 分桶收集，只在选中后回放胜者的事件（避免 doom-loop 检测器吃到别的候选的 bash 记录）。
- 错误隔离：单候选异常只影响该候选（记入 `failures`），不冒泡。
- 成本累加：把各候选 `Types.usage_stats` 累加进本回合 `cost`。

### W2 — 选择器 🔴P0

新模块 `lib/par_code_selector.ml`（+ `.mli`）：

- 注册 `selector` agent（`tools:[]`、`max_iterations:1`、`model` 同 judge 配置），system prompt 要求输出 JSON：`{"choice": <int>, "kind": "answer"|"execute", "plan": "<给执行阶段的指令，可空>", "reasoning": "<一句话>"}`。
- 输入：用户消息 + 编号候选文本（每条截断到 ~2000 字符，避免 token 爆掉）。
- 解析：复用 `par_code_judge.ml` 的 `extract_json_object` 思路（**不直接复用**：judge 的解析函数未导出，抽出到共享小模块或在 selector 内独立实现一份最小版本——两处都要用同一套宽松解析语义）。
- 回退：解析失败/choice 越界 → `choice=0`、`kind=answer`。
- 走 `Runtime.invoke_generate ~save:false ~update_current:false`（与 extractor 同款调用姿势）。

### W3 — REPL 接线与会话接管 🔴P0

- 回合入口（`par_code_repl.ml:515` 附近）加分支：`max_mode` 开启且非 goal-chain 续跑 → 走候选流程，否则维持现状。
- 候选阶段渲染：每个候选一行状态（`Par_code_ui.render_line`），不打断当前 markdown 状态机。
- 选择后：
  - `kind=answer` → 接管**胜出候选的 conversation**（`conv := Some winner_conv`），渲染胜者最终文本（走 `Par_code_ui.render` + `Par_code_ui.text`），落库 `Runtime.save_conversation`。
  - `kind=execute` → 接管胜出会话，把 `plan` 作为下一条 user message 交给**正常 build 回合**（流式照旧），由它执行落地。
- 落库语义与现有路径一致：胜出会话接管后由 REPL 统一 `save_conversation`；候选过程中的中间会话**不落库**（`~save:false`）。

### W4 — 测试 🟡P1

- 单元（`test/test_par_code_max_mode.ml`）：策略种子拼装、候选文本截断、选择器 JSON 解析（含缺字段/越界/非 JSON 三种脏输入）、回退到 0 号、会话副本不被改写、成本累加。
- 单元（`test/test_par_code_config.ml` 扩展）：两个新字段的默认值、旧 JSON 配置缺字段时的兜底、`par config set` 往返。
- 单元（`test/test_par_code_selector.ml`）：与 judge 解析语义一致的脏输入矩阵。
- 集成：复用现有 "dead endpoint" 手法（见 `test/` 里的 goal chain 集成文件）验证"候选全失败 → 回退单路 invoke"。

### W5 — 文档同步 🟡P1

- `README.md`：roadmap 表 v0.8.0 行改为 ✅ + 能力描述；配置表加 `max_mode` / `max_candidates`；新增 `/max` 命令说明。
- `CHANGES.md`：v0.8.0 段落。
- `docs/STRATEGY.md`：roadmap posture 行更新。
- `AGENTS.md`：文件索引新增 `par_code_max_mode` / `par_code_selector`。
- `docs/DECISIONS.md`：本 ROADMAP 的范围决策 + PAR SDK feedback 两条。

### W6 — PAR SDK feedback 归档 🟢P1（不阻塞实现）

见 `docs/DECISIONS.md` 同日条目：① 并发原语缺会话维度（`invoke_parallel` 分支无 conversation、只回 JSON）；② `invoke_async` 缺 `?save` / `?update_current`（旧 feedback 复提）。两条都不阻塞 v0.8.0——par-code 侧按 §3 决策 1/3 自行编排。

## 5. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 候选成本 N 倍 | 用户 token 账单上升 | 默认关闭 + `/cost` 显示本回合 N 路累加 + README 明示 |
| 候选同质化 | 白花 N 倍 token | 策略种子（决策 6）+ 选择器 prompt 要求"按正确性/完整度/简洁度"排序 |
| 选择器误判 | 选到差答案 | 失败回退 0 号；选择器输出附一行理由让用户可判断 |
| 候选探索把上下文撑大 | 接管胜出会话后 context 变长 | 候选 `max_iterations` 控制在 8–10；胜出会话即父会话，触发既有 compaction |
| 并发候选污染父会话 | 历史串味 | 决策 3（`~update_current:false` + 显式会话副本），并加断言测试 |
| 自主 goal 循环里 N 倍成本 | 费用失控 | goal chain 续跑时跳过 max mode（§2.3） |

## 6. 执行顺序（建议 wave）

- **Wave 0（阻塞）**：v0.7.5 落地——SDK 地板升到 `0.11.0-beta.20261013`、CI pin 改 tag、`invoke` / `conversation` 语义在新地板上复核一遍
- **Wave 2（依赖 W0/W2）**：W1 候选执行器 → W3 REPL 接线
- **Wave 3**：W4 测试补齐 → W5 文档同步
- **Wave 4**：真机 dogfood（3 场景：问答类、改造类、失败回退类）→ 决定是否发 v0.8.0
