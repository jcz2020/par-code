# v0.16.0 · 会话库回收（Storage reclaim）

> 状态：已实现（2026-11-27，未发布）。版本号 v0.16.0 为暂定，发布时以 `dune-project` 为准。
> 前置：v0.15.9（启动/退出只做局部工作）已发布；本计划处理它留下的 `CHANGES` Known limit。

## 背景

- 一个会话在 `conversations.messages_json` 里存成单行 JSON；删除旧会话、清理记忆之后，SQLite 只把页放回 freelist，**文件本身不缩小**。
- 本机实测：`~/.par/par.db` 目前 9.2 MB / 105 个会话、最大会话 262 KiB；此前清掉的大会话曾让库长期停在 649 MB，其中约 650 MB 是空闲页。
- 归属判定：`conversations` 表、读写与保留期都由 PAR SDK 的 `Sqlite_persistence` 拥有（`lib/par_code_session.ml`、`lib/par_code_setup.ml` 只接线）；par-code 只额外挂了 `conv_ai/ad/au` 三个 FTS 触发器。
  - **空闲页回收 = 纯数据库维护，宿主侧可做。**
  - **「每轮保存整段重写会话」= SDK 行为，不在本侧重写存储**；按项目规矩另开 issue 报给 PAR，等上游。

## 目标

1. 删掉的会话/记忆占用的磁盘空间可以被真正还给文件系统，而不是只留空闲页。
2. 回收是显式、可预期、可度量的：用户能先看到「现在多少、回收后多少」。
3. 不破坏 v0.15.9 的启动/退出指标（首帧 ≤ 0.5 s、退出 ≤ 0.5 s），不把回收放进启动热路径。

## 非目标

- 不改 SDK 的 `conversations` 表结构，不拆 messages 表，不对 `save_conversation` 做替代实现。
- 不在启动路径上做全量 `VACUUM`（大会话上是秒级到分钟级）。
- 不动记忆条目的保留策略、不做压缩编码（zstd 等）。

## 方案

采用 SQLite 原生的两种回收方式，默认走增量：

- **增量回收**：把库的 `auto_vacuum` 设为 `INCREMENTAL`（一次性转换需要一次全量 VACUUM），之后删除产生的空闲页用 `PRAGMA incremental_vacuum` 按页释放，代价与释放量成正比，适合在 prune 之后顺手做。
- **全量回收**：`VACUUM`，一次性重写整库；只在用户显式要求时执行，用来做首次转换或收拾历史遗留的空闲页。

对外接口：

- `Par_code_memory`：暴露空闲页统计（`freelist_count`、`page_count`、`page_size`，换算成字节）与 `reclaim ~mode:[`Incremental | `Full]`。
- CLI：`par memory vacuum [--full]`——默认增量（必要时先做一次全量转换并明说），`--full` 强制全量。输出「回收前 / 回收后 / 释放字节」，失败按现有错误风格返回非零。
- `par memory prune` 删除行之后，若库已是增量模式则顺手 `incremental_vacuum`；未开启增量模式的库保持原样（不加隐式全量 VACUUM）。

## 阶段

1. **测量**（本机 sqlite3，合成库，不动真实 `~/.par/par.db`）：造 100–300 MB 数据 → 删除大部分 → 记录文件大小、`freelist_count`；分别测 `VACUUM` 与「转增量 + `incremental_vacuum`」的耗时与体积变化。
2. **API**：`freelist_bytes` / `reclaim` 两个函数 + 单测（含 auto_vacuum 未开启、已开启、无空闲页三种情形）。
3. **CLI**：`par memory vacuum [--full]`，接 `main.ml` 与 `cli_args`（新增 flag 需同时在 `cli_args.ml` 与 `main.ml` 接线）。
4. **prune 联动**：`prune_stale` 后按模式决定是否增量回收。
5. **验证与文档**：proot 里 `dune runtest` + 真实库副本上的回收演练 + CHANGES / DECISIONS / AGENTS.md（lib 段）同步。

## 验收标准

- 合成库：删除 200 MB 数据后 `par memory vacuum` 让文件大小下降 ≥ 删除量的 80%；`--full` 与默认模式都能结束在「空闲页接近 0」。
- 真机副本：把 `~/.par/par.db` 复制一份制造空闲页，回收后 `du` 明显下降，`memory search-history` 与 `session list` 结果不变。
- 指标不回退：首帧 ≤ 0.5 s、空闲退出 ≤ 0.5 s（与 0.15.9 实测 263–329 ms / 134 ms 同量级）。
- `dune runtest` 35 个 suite 全绿；`cli/memory` 集成用例覆盖 `vacuum` 的参数与输出。

## 回滚

- 去掉 CLI 子命令与 prune 联动，`Par_code_memory` 的两个新函数保留或删除均可，不影响既有路径。
- `auto_vacuum` 一旦开启是库级持久设置；回滚不需要改回（INCREMENTAL 只影响页分配方式，不改变数据）。
- 不做任何 schema 迁移，因此没有数据回滚风险。

## 风险

- `VACUUM` 需要一次独占事务并可能临时占用约等于库大小的磁盘空间；低磁盘设备上要先检查剩余空间再执行。
- 增量模式会给删除操作带来少量指针表开销（页级，可忽略，但需在测量阶段记录）。
- 正在写入的会话不受影响：回收只发生在 prune 之后与显式命令中，复用同一条 SQLite 连接。

## 实施记录（2026-11-27）

- 合成库（210 MB，删掉 180 MB）：全量 `VACUUM` 146 ms、增量 308 ms，两者都缩到 21 MB，freelist 归零。
- 真实库副本演练（9.6 MB 的 `~/.par/par.db` 复制后注入 30 × 8 MB 假会话再删除）：`par memory vacuum` 94 ms，246.0 MiB → 6.2 MiB，free pages 61,384 → 0；`memory search-history`（10 行）与 `session list`（1 行）输出前后一致。
- 单测：`test_par_code_memory.ml` 新增 `storage` 三例（全量、增量转换、prune 联动），全套 35 个 suite 通过；集成 `cli/memory_test.sh` 新增 `memory vacuum` 用例通过。
