## 0. 主题与范围

**一句话**：让 `/goal` 从"演示可用"变成"真实任务可用"——agent 撞到护栏时有出路、卡死时有信号、失控时护栏真的会停、**等待时用户看得见**；plan mode 同源问题一并修。

| 维度 | 决定 |
|---|---|
| 版本类型 | MINOR（v0.7.2），纯增量 + 行为修复，无破坏性 API 变更 |
| 核心用户价值 | *"It can actually finish a goal — and you can see what it's waiting for."* |
| **做** | 隐形等待点修复（W0）、bash/write 审批策略（W1）、planner 综合兜底（W2）、doom-loop 真实拦截（W3）、goal 生命周期硬化（W4）、卡死与漂移可见性（W5）、resume 复查（W6） |
| **不做** | ① 全自主 goal chaining → **推迟到 v0.7.3**；② 完整 permission 规则引擎 + 审批 UI → 维持 v0.13.0，本版只做"最小审批策略 + pattern 持久化子集"；③ MCP/workflow（维持 v0.10/v0.11）；④ fallback plan 文件自动清理（`par plan prune` 已覆盖） |
| 范围决策记录 | 见 §6；随本 ROADMAP commit 时同步 `docs/STRATEGY.md` roadmap 列表与 README roadmap 行 |

**状态语义总规则**（全文档冻结，W3/W4/W5 共同遵守）：
- **`Aborted`** = 硬停止，单向，不可 resume。仅 doom-loop Abort 和 max_steps 用。
- **`Blocked of string`** = 软停止，带原因，`/goal resume` 可恢复。no-progress（W5）、verify 失败、护栏拒绝后 agent 无路可走时用。
- 现有 `Paused` 保留给用户显式 `/goal pause`。

**设计参考**（泛化引用，遵守披露规则）：三个业界 harness 架构的公开设计——工具执行管线（pre-execute 审批瀑布：allow/ask/deny 三态 + 单次审批 + 单调护栏）；事件溯源 goal 生命周期（verbs 全集含 blocked、activation 仅进程内）；低收益循环检测（三信号 + 输入归一化 + 命中即暂停并持久化证据）。另有同模型对照走查中对齐目标项目编译产物的源码级核读结论（机制描述见各工作项，不指名来源）。

### W1 — bash/write 审批策略 v2 🔴P0

**问题**：现状"凡 bash 必问"（22 词 safe-list 之外），非交互 goal 场景被堵死；无"记住批准"；write 拒绝绝对路径的错误无出路。

**"项目根"定义**（两层拆分，2026-08-15 SDK 核读后冻结）：
- **启用闸门**：从进程 CWD 向上找到 git 根才激活 auto_project（防裸目录乱放行）；无 git 根 → `auto_project` 降级为 `ask`
- **分类边界**：`Par.Workspace.of_cwd ()`（SDK Runtime 自用同一构造，`runtime.ml:2065`）——单根 = 进程 CWD，**不认 git worktree**（SDK 多根构造器存在但 Runtime 未使用，与 SDK 的 write/bash 沙箱边界天然一致：auto_project 放行范围 = write 工具可写范围，不会出现"审批放行但沙箱拒绝"的错位）

**判定输入**：hook 收到的 cmd JSON 的 `argv` 数组（已可见，见 `par_code_setup.ml:510` 解析）；`sh -c` 内嵌命令串用正则扫重定向目标（`>\s*(\S+)`）与路径样 token。

**三分类判定**（分类核心直接映射 SDK 现成 API `Par.Workspace.admit : workspace -> string -> (sandboxed_path, error) result`，公开导出于 `par.ml:15`——比手写前缀比较多出路径规范化、`..`/`:` 拒绝、敏感前缀（/etc、~/.ssh）三层防护；SDK 侧零改动）：

| 分类 | 判定（对每个路径样参数/重定向目标调 `Workspace.admit`） | 行为 |
|---|---|---|
| `in_project` | 全部 `Ok _`，且命令不在删除类黑名单（rm/mv 覆盖写/dd 等） | auto_project 模式下放行；ask 模式下仍问 |
| `external_path` | 任一返回 `Error (Invalid_input "absolute path not under any workspace root")` | 必问（goal 模式也不豁免），提示中列出外部路径 |
| `sensitive` | 任一返回 `Error (Permission_denied _)`（/etc、~/.ssh 等） | 必问 + 提示敏感路径 |
| `unknown` | 解析失败/无法判定（嵌套 shell、命令替换等） | 必问（fail-closed） |

**always-pattern 持久化**（permission 引擎的最小子集，v0.13.0 完整版的前身）：
- 确认提示三选项：`[y/a/N]`（y=本次，a=always，其他=拒绝）——结果词汇对齐 SDK 已有的 `Par.Approval.approval_outcome`（Approved/Rejected/Timeout；其 Async_callback/Webhook handler 形态为未来 headless 审批留路，本版只消费语义不接线）
- 选 a → 前缀 pattern 写入 `.par/approvals.json`（如 `pytest *`、`/tmp/*` 目录 pattern）
- hook 判定前先查 patterns 命中即放行；`par config set bash_approval ask` 不清 patterns（独立文件，`par` 无 CLI 管理入口本版不做，手编即可）

**config 字段**：`bash_approval : ask | auto_project | always`（默认 `"ask"` 行为不变）。goal active 时生效模式 = `max(用户配置, auto_project)`（放行程度单调序 ask < auto_project < always；`always` 优先）。

**write 工具错误文本**：实现在 PAR SDK（`workspace.ml`）→ 记 **PAR SDK Feedback**（加入出路指引文本）；par-code 侧过渡：build/planner agent system prompt 预写一句"写文件用项目相对路径；绝对路径会被拒"。

**文件**：`lib/par_code_config.ml`（+1 字段 ×9 触点，wizard 含 always 警告）、`lib/par_code_setup.ml`（confirm_fn 重构为策略函数 + 三分类判定 + patterns 读取）、`lib/par_code_ui.ml`（prompt_confirm 三选项版）、`.par/approvals.json` 读写（新小模块或并入 config）、`test/integration/cli/config_set_test.sh`（+1 字段）、`docs/DECISIONS.md`（Feedback 条目）

**QA**：
- CI：`always` → 触发 bash 无 `[y/N]`；`auto_project` + `ls lib/` → 免确认；`auto_project` + `ls /etc` → 出现确认且提示含 `/etc`；选 `a` 后同前缀命令免确认（重启进程后仍免确认——patterns 持久化）

### W2 — Planner 强制综合兜底 🟡P1（走查后从 P0 降级）

**降级理由**：同模型走查中同一 prompt 六节全对——planner 不合规是特定模型（1.1 中的模型 A）的 prompt 合规问题，非普适缺陷。保留为防御性兜底。

**触发条件**（冻结）：invoke 返回后 `consume_submitted_plan () = None` **且** `.par/plans/` 中无 mtime ≥ 本次 invoke 开始时间的文件（防 write_plan_file 已落盘但 plan_submit 未调的场景被重复覆盖）。

**方案**：
- 触发时一次 `invoke_generate` 综合调用（`~save:false ~update_current:false`，注入"基于以上调研立即产出完整 plan，必须包含六节"），落盘该输出
- **递归边界**：至多 1 次；综合输出仍缺任一节 → 落盘原始 preamble + `[plan synthesis failed — saved raw planner output to X]`，不重试
- planner prompt 收紧：`write_plan_file` 给字面调用模板
- 文案区分：`planner stopped early — synthesized plan saved to X` / `planner hit iteration cap — synthesized plan saved to X`
- **plan→build 闸门体验**（并入 W0a/b 修复后验证）：闸门可见 + declined 中性语义；走查中"agent 误判取消→再存垃圾 plan"链条应消失

### W3 — Doom-loop v2：真实拦截 + 三信号 🔴P0

**问题**：现有检测只 hash 完全相同连续调用（A-B-A-B、近似重复测不到）；`Abort` 只 print 不 abort。

### W4 — Goal 生命周期硬化 🟡P1

**问题**：状态机缺"卡死"表达；`clear`/`mark_status`/`advance_step` 不刷盘；重启后续跑语义不明。

**verbs 全集**：`set / pause / resume / complete / block(reason) / clear`。

**落盘语义**（冻结）：
- `set/pause/resume/complete/block` → 变更后立即写 `current.json`（status + step_count + blocker reason + updated_at）
- `clear` → 删除 `current.json`（"已清"以文件不存在为准）
- `advance_step` → 随下一次状态写盘落盘（崩溃丢 step 计数可接受）

**status 类型升级**：`Blocked of string`。改动清单：
1. 类型变体（`par_code_goal.ml:1`）
2. `status_label`（`Blocked r` → `"blocked: " ^ r`）
3. `to_json`/`of_json`——status 编码 `{"kind":"blocked","reason":r}`；旧 schema 纯字符串照常解析，未知值 → `Active` + 警告
4. 新函数 `pause_goal / resume_goal / block_goal`（resume 仅接受 `Paused`/`Blocked _`，`Aborted` 拒绝）
5. `/goal` 子命令解析（`repl.ml:330-350`）：`/goal pause`、`/goal resume`、`/goal`（显示含 blocked reason）

**activation 只在内存**：重启/`--resume` 后 goal 状态恢复但**不自动续跑**——显示 `[goal restored: X (step N/M, <status>) — /goal resume to continue]`。

**judge 触发保持**：steps 3,6,9,…（`step mod 3 = 0`）+ `goal_done` 立即（显式化，不变）。

**文件**：`lib/par_code_goal.ml`、`lib/par_code_repl.ml`（/goal 解析 + 恢复横幅）、`test/test_par_code_goal.ml`

**QA**：CI 单测（verbs 刷盘 / 旧 schema 读入 / resume 对 Aborted 拒绝）；CI 集成（tmux 无 LLM）：`/goal X` → `/goal clear` → current.json 不存在；预置 active current.json → 启动 → restored 横幅 + 3s 内无工具活动；kill -9 → 重启 → restored。

### W5 — 卡死与漂移可见性 🟡P1（走查后扩展）

**问题**：agent 撞墙后静默放弃（躺平）；或做错任务后**自报完成**（漂移）——走查 T3 实锤：修错文件、pytest 仍红、宣告"已完成"，goal 全程沉默。

**"无进展"定义**（冻结，与 W3 分工：W3 管"打转"（有动作无改善），W5 管"躺平"与"漂移"）：

> invoke 返回后本轮：**工具调用数 = 0** 且 **未调 `goal_done`** 且 **assistant 文本 < 200 字符** → 无进展。

**漂移检测（本版新增，对齐"不信任自报完成"原则）**：
- **确定性验证优先**：goal active 时若 config 有 `goal_verify_command`（v0.7.0 已有字段，从未接线）→ 每次 invoke 返回后先跑 verify command：exit 0 → 可信完成；非 0 → `block_goal "verify_failed"` + 把 verify 输出注入下一轮 judge feedback
- **完成宣告复核**：agent 文本含完成宣告模式（"已完成"/"完成"/"done" 启发式）但未调 `goal_done` → 强制触发一次 judge（不复信自报）
- 两路都通向 W4 的 Blocked/Met 状态机

**行为**：
- 首次无进展 → `block_goal "no_progress"` + `[goal: no progress this round — blocked; /goal resume to retry, /goal clear to abort]`
- 连续 2 轮 → `block_goal "no_progress_x2"`
- blocked 状态不自动续轮（依赖 W4）

**文件**：`lib/par_code_repl.ml`（invoke 返回后 goal 分支扩展；工具计数从 `on_tool_event` 计数；verify command 执行经 bash-safe 路径）、`lib/par_code_goal.ml`（依赖 W4）

**QA**：CI 单测判定函数（0 工具+短文本→true；200+ 字符→false；有工具→false）+ verify command exit code 分流；LLM dogfood 复跑走查 T3（同款 goal + `goal_verify_command="python3 -m pytest tests/ -q"`）——期望 agent 修错方向时 verify 红 → blocked + 反馈 → 纠偏。

## 5. 风险

| 风险 | 缓解 |
|---|---|
| auto_project 的 argv+正则判定被绕过（嵌套 shell/命令替换写外部路径） | fail-closed：解析不了必问（unknown 分类）；`sh -c` 内嵌串必须扫完重定向与路径 token 才可判 in_project；bash-safe 注入防护叠加其上不替代；无 git 根降级 ask |
| always-pattern 被过宽授权（`* ` pattern） | pattern 仅前缀匹配且写入时提示范围；`.par/approvals.json` 纯文本可手改可审计；完整规则引擎（deny 优先级、目录级粒度）留 v0.13.0 |
| 完成宣告启发式误报（"完成了分析"≠任务完成） | 启发式只触发 **judge 复核**（多花一次 judge 调用），不直接改状态；verify command 优先且确定性 |
| 强制综合多花一次 LLM 调用 | 至多 1 次，失败止损（preamble + 显式提示） |
| doom 三信号误伤正常迭代 | edit_repeat 近似匹配（Jaccard）而非同文件；阈值全可配；nudge 只提示；归一化防时间戳/seed 误判 |
| PAR SDK 缺取消 API → W3 轮内拦截缺失 | 降级语义：轮间拦截 + 诚实文案；Feedback 已记 |
| W2/W4 并行改 repl.ml 冲突 | 分区无重叠（fallback 区 vs /goal 区）；W0 提前合并降低后续冲突面 |

## 6. 决策记录（随 commit 并入 DECISIONS.md）

**[2026-08-15] v0.7.2 范围：autonomous chaining 推迟一版**

- **变更前**：STRATEGY.md roadmap 排定 v0.7.2 = 全自主 goal chaining
- **变更后**：v0.7.2 = goal/plan 可用性收尾（本 ROADMAP）；chaining 移至 v0.7.3
- **原因**：两轮实测（QA + 同模型对照走查）证明 goal mode 在真实写任务上完全不可用：三个隐形等待点（R1/R2/R4）+ goal 漂移零防护（R3）+ 护栏说谎。对照走查中同模型双 agent 同任务，对齐目标三局全胜且全部胜在 harness 层——在单轮跑不通、用户看不到等待点的地基上叠加自动续轮会放大失控
- **影响范围**：排期推迟一版；v0.7.2 工作量（W0-W7）与 chaining 原估相当
- **回退方式**：v0.7.2 完成且 dogfood 良好 → v0.7.3 chaining 直接开工，无结构性锁定
- **已知限制**：auto_project 是 argv+正则近似而非语法解析级 AST 判定（对齐目标用后者；par-code 引入语法解析器的成本留待 v0.13.0 评估）；轮内强制终止依赖 PAR SDK 反馈进度；W6b/W0c 验证依赖人工 dogfood
