# 宿主侧可靠性对齐计划（v0.15.7）

> 冻结于 2026-11-22。本文件是这一轮「达到行业通用水平」的验收基线：目标、非目标、阶段、判据、回滚都写在这里，实施按阶段推进。
> 上游 `jcz2020/par#44` 正在处理网络层取消与引擎级工具结果上限；本计划只做宿主侧能独立完成的部分，上游落地后删掉重复兜底，不在 par-code 自建替代实现。

## 目标

让「工具结果、取消、中断」三件事和成熟编码 agent 一致：

1. **所有工具结果统一封顶且可恢复**：内置工具与 MCP 工具都受同一个上限约束；超限内容落盘，对话里返回预览和文件路径，模型可以自己分段读；文件按保留期清理。
2. **强制取消保留已经发生的半轮**：用户消息、已完成的工具结果留在会话里，下一轮模型知道刚才做了什么；不产生空会话。
3. **键盘语义没有歧义**：弹窗里 `Esc` 只拒绝当前工具，`Ctrl-C` 取消整个回合，状态栏如实显示两者；回合运行中 `Esc` 仍然是中断。
4. **取消覆盖所有用户可见的 invoke**：主回合、max-mode 候选、`/distill`、`/flow run` 都能被 `Esc` 在一秒左右停下；后台 checkpoint 提取不强行取消。
5. **回归测试固化**：静默 provider、超大 MCP 结果、弹窗按键三条故障路径进仓库并进 CI，避免以后回退。

## 非目标

- 不改 `/root/dev/PAR`，不提 PR，不等 #44；不因为等上游而停掉宿主侧工作。
- 不在 par-code 重建 provider 取消层或工具注册体系；宿主 `Eio.Fiber.first` 兜底保留，上游修好后可简化。
- 不改 bash / edit 审批策略本身，只改弹窗提示与按键语义。
- 不新增 TUI 功能（不做主题、命令面板、多工作区、插件槽）。
- 不提高默认 32K 上限；只把它变成可配置，默认值保持现状。
- 不把 MCP 工具 schema 无限制塞给所有子 agent；启动时只挂主 agent，子 agent 维持现有白名单。

## 已确认的 SDK 事实（PAR 0.17.3-beta.20261118）

- 工具结果原样进入会话；`Context_manager.truncate_conversation` 只能整条丢消息，所以单条超大消息无法靠压缩解决。引擎级上限需要上游（#44）。
- MCP 绑定可被宿主接管：`Runtime.mcp_tool_bindings` 返回 `(descriptor, handler)`；`Runtime.update_agent_tools ~add` 会注册/替换 handler（`register_or_replace_tool_handler`），`Runtime.replace_tool` 可替换已注册工具。MCP 工具目前在 `/mcp reload` 路径才挂到 agent，启动路径没有挂载，需要在本计划里补齐并统一包装。
- 持久化检查点可只读读取：`Par.Types.persistence_service.load_invoke_checkpoint_fn : string -> (invoke_checkpoint option, error_category) result`，`invoke_checkpoint.conversation` 是完整会话；`Runtime.recover_invoke` 会重跑未完成的工具，不适合「只保存半轮」。
- 取消 token 是原子标志；provider 在完全静默时不会观察它。主回合已用 `Eio.Fiber.first` 让取消标志取消阻塞读；其他入口尚未覆盖。
- `.par/` 已在 `.gitignore`，落盘文件不会再进仓库。

## 阶段 1 —— 统一结果上限与落盘（大）

**配置**（`par_code_config.ml`，向导同步）：

- `tool_output_chars`：默认 `32768`，允许 `1024..1000000`；<=0 视为非法。
- `tool_output_retention_days`：默认 `7.0`；`0` 表示不清理。

**行为**：

- 结果序列化后 `<= tool_output_chars`：去掉 NUL 等 C0 控制字符后原样返回（保持现有行为）。
- 超过上限：完整结果原子写入 `.par/tool-results/<UTC 时间戳>-<tool 名>-<随机后缀>.txt`（权限 `0600`），返回「前 `tool_output_chars` 个字符 + 尾部标记 + 文件相对路径」。列表结果保留头部能放下的项，完整列表落盘；模型用 `read` 按 offset/limit 自己读。
- 清理：启动时与每次落盘后执行，删除超过 `tool_output_retention_days` 天或数量超过 200 的旧文件（先到者为准）。
- `sanitize` 在载入/保存旧会话时仍做截断，但不落盘（避免加载时写盘）；只把 Tool 消息截到上限并去控制字符。

**MCP**：

- 新增一个 helper：把 `Runtime.mcp_tool_bindings rt` 逐个包一层 `cap_handler_result`，然后对目标 agent 调用 `update_agent_tools ~remove:(names) ~add:(wrapped)`。启动注册主 agent 后调用一次（同时修复「只有 /mcp reload 才能看到 MCP 工具」）；`/mcp reload` 改走同一个 helper。
- 只挂主 agent + 本来就有 MCP 工具的 agent（沿用 reload 现有判定），`explore` 保持只读白名单。
- 包装只针对本次从 SDK 取到的新 handler；每次 reload SDK 都给新绑定，不叠加层数。

**落点**：`par_code_payload.ml/.mli`（cap + spill + retention）、`par_code_setup.ml`（工具与 MCP 包装）、`par_code_repl.ml`（`/mcp reload` 复用 helper）、`par_code_config.ml`、`par_code_config_wizard.ml`、对应测试。

**判据**：

- 一个返回 5 MB 的假 MCP 工具和一个返回 5 MB 的内置工具：会话里的 Tool 消息不超过 `tool_output_chars + 200`；`.par/tool-results/` 下的文件字节数与原始结果一致；下一轮模型能通过路径 `read` 到全文。
- 同一工具多次调用不产生重复包装；`/mcp reload` 前后行为一致。
- 保留期与数量清理有单测；`tool_output_chars` 的边界值有配置测试。

**回滚**：把 `tool_output_chars` 配成 `1000000` 可关闭截断；删除 spill/retention helper 与 MCP 包装调用即恢复现状。

## 阶段 2 —— 强制取消保存半轮（中）

**行为**：

- 主回合 `Runtime.invoke` 传宿主生成的 `~invoke_id`（uuid），记在 `current_invoke_id`；正常结束/取消后清空。
- 强制取消（`Eio.Fiber.first` 的取消分支）按以下顺序取会话：
  1. `Par_code_setup.persistence ()` 的 `load_invoke_checkpoint_fn id` 返回 `Some cp` → 用 `cp.conversation`；
  2. 没有检查点 → 用回合开始前的会话 + 原始用户消息（避免把这轮的问题丢掉）；
  3. 两者都为空 → 不保存，不新建会话。
- 保存前走 `Par_code_payload.sanitize`；不追加伪造的 assistant 文本，界面继续显示 `⊘ [cancelled by user]`。
- 检查点只覆盖「已完成的工具批次」；正在执行的工具可能已产生副作用，取消后照旧在界面上提示用户先核实（沿用现有文案，不新增假状态）。

**判据**：

- 静默 provider 上先让模型调用一次 `bash echo`（已完成的工具批次），再卡住、按 Esc：下一轮会话历史里能看到这轮用户消息和那次工具结果；没有空会话。
- 没有任何检查点的首轮静默取消：保存用户消息，下一轮模型能看到这轮问题；会话不为空。
- 正常取消、正常结束路径不变；`/resume` 的孤儿检查不把已保存的会话当孤儿。

**回滚**：去掉 `~invoke_id` 与恢复分支，强制取消回到「保留回合开始前会话」。

## 阶段 3 —— 弹窗与按键语义（小）

**行为**：

- 状态栏右侧提示按上下文变化：
  - 回合运行、无弹窗：`esc interrupt`；
  - 弹窗打开：`esc deny · ctrl-c cancel`（窄屏退化到 `esc deny`）。
- 弹窗内按键：
  - `Esc`：拒绝当前工具，返回 `Block`，回合继续（现状）；
  - `Ctrl-C`：拒绝当前工具，并置 `cancel_request`，由 ticker 消费后取消整个回合（现有 `poll_interrupt` 在 modal 打开时不读键，需要新增一个屏幕级标志，由 ticker 在 modal 时也轮询）。
  - `y` / `a` / `n` 语义不变。

**落点**：`par_code_screen.ml/.mli`（状态栏 hint、cancel_request、modal 键处理）、`par_code_repl.ml`（ticker 消费 cancel_request）、屏幕提示的纯函数测试。

**判据**：

- 弹窗打开时状态栏不再出现 `esc interrupt`；按 `Esc` 看到工具被拒绝、回合继续；按 `Ctrl-C` 一秒内回到空闲。
- 窄屏（80 列）下提示不被截断成歧义文案。

**回滚**：恢复旧 hint 与 modal 键分支；`cancel_request` 字段保留但不消费。

## 阶段 4 —— 取消覆盖其余入口（中）

**范围**：

- max-mode 的 `Par_code_max_mode.run_candidates`；
- `/distill` 的模型调用；
- `/flow run` 的同步 workflow；
- 其他同步等待用户输入的入口按同一 helper 处理。

**行为**：抽一个 `with_interrupt clock ~cancelled f` helper（`Eio.Fiber.first` + 0.05s 轮询），主回合也改用它，避免复制。后台 checkpoint / extractor / judge 不接入用户取消，保持完成。

**判据**：上述每个入口按 `Esc` 后一秒内停止；不留下孤儿 invoke；`/distill` 取消后不写提案文件；flow 取消后不继续跑下一步。

**回滚**：逐入口移除 helper 包装，只保留主回合。

## 阶段 5 —— 回归测试与文档（中）

- 集成测试（`test/integration/`）：
  - `silent_provider`：本地 SSE 服务收下请求、发 headers 后不再写字节；启动 TUI，提交一条消息，按 `Esc`，断言一秒内回到空闲且没有新增空会话；tmux 缺失时 SKIP。
  - `huge_mcp_result`：假 MCP 服务返回 5 MB；断言 Tool 消息 ≤ 上限、落盘文件存在且字节数正确。
  - `modal_keys`：真跑一次 bash 审批，分别按 `Esc` / `Ctrl-C`，断言前者只拒绝工具、后者取消回合并显示正确 hint。
- 单元测试：cap/spill/retention/config 边界；`recover_after_cancel` 纯函数；状态栏 hint 纯函数。
- 文档：README 配置键说明；`docs/DECISIONS.md` 六字段条目；`CHANGES.md` 发布段落。

**判据**：`dune build` 与全量 `dune runtest` 绿；集成用例在 CI 的 Linux job 上跑，tmux 缺失只 SKIP 不失败。

## 依赖与顺序

阶段 1 独立，先做；阶段 3 最小，紧随其后；阶段 2 依赖持久化接口；阶段 4 复用阶段 2/3 的取消路径；阶段 5 跟着每个阶段补测试，最后统一过 CI。按 **1 → 3 → 2 → 4 → 5** 推进。

## 风险

- 启动时挂 MCP 工具会扩大模型可见 schema；先只挂主 agent，必要时用 `max_tool_schema_tokens` 控制。
- 落盘内容可能含敏感数据：`0600` + `.par/` 已忽略 + 保留期清理；README 写明。
- 强制取消的恢复只到最后一个完成批次，正在执行的工具可能已有副作用；界面提示用户核实。
- max-mode / flow 取消可能留下候选会话或半成品；沿用现有「候选不保存」策略，不新增清理逻辑。
