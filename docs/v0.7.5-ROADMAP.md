> 状态：**已实现，待发版**（2026-11-01）。3 处必修点、五个安装点的 tag pin、`apply_patch` 采纳与 prompt 指引、doom-loop 对 `apply_patch` 的归类、行为差异文档化均已完成；本地 `dune build` / `dune runtest` 与集成套件全绿。发版仍需用户明确说"发布"。

> 前置证据：① 已装 SDK（0.10.0）vs PAR 仓库当前状态的**类型级漂移审计**（7 个 `.mli` 有差异，逐个对照 par-code 的穷举匹配点与调用点）；② 本机 opam switch、`git` 实测；③ CI 与 release workflow 逐行核读；④ 一手复核审计的关键结论（编译破坏点、无通配的 match、工具分层实现）

## 0. 主题与范围

**一句话**：把 PAR SDK 从 0.10 追到 0.12-beta（拿到 `apply_patch`、bash 输出完整性修复），顺手把"每次构建都从上游分支 tip 取 SDK"这个不可复现的坑填掉。

| 维度 | 决定 |
|---|---|
| 版本类型 | PATCH（v0.7.5），依赖跟进 + 能力采纳，无破坏性变更 |
| 核心用户价值 | *"It edits more reliably, gets complete command output, and its build stops depending on whatever upstream's branch tip happened to be."* |
| **做** | W0 构建可复现化（pin 到 tag + 记录 SDK 版本）｜W1 SDK 地板 bump + 2 处必修编译点 + 1 处 match 补 arm ｜W2 `apply_patch` 采纳（工具可见性 + system prompt 指引 + 文档）｜W3 两条行为差异的文档化 ｜W4 验证（本地绿 + CI 绿 + dogfood） |
| **不做** | ① 渐进式工具加载开关（开了等于没开，§2 C10 + 决策 5）；② 不用 `Runtime.register_agent_as_tool` 替换自研 delegate（决策 3）；③ 多模态输入（决策 4）；④ 不动任何行为默认值 |

**为什么是 patch 而不是 MINOR**：三个采纳项里 `apply_patch` 对用户是**零代码自动生效**（主 agent 本来就用全量工具描述符），bash 修复是纯上游内部修复，delegate 保持原样——合起来没有新交互面、没有新状态机、没有默认值变更。真正的能力增量（max mode）留在 v0.8.0。

1. **已发布二进制不可复现**：v0.7.3 的构建取的是 2026-08-17 那一刻的 PAR 分支 tip。

## 3. 范围决策记录（R1 判定）

| # | 决策 | 判定 | 理由 / 退役条件 |
|---|---|---|---|
| 1 | 地板提到 `(par (>= 0.12.0-beta.20261023))`，CI/release 的 pin 改为 **tag** `v0.12.0-beta.20261023`，并在发布说明记录 SDK 版本 | **架构正确**（"PAR 未上公共 opam"约束下唯一可复现钉法） | 一次升到最新 tag，避免 0.11→0.12 再来一次 bump；两次之间的差异只有多模态（推迟）+ web 上限（写文档）+ bash 修复（纯改进）。**退役条件**：PAR 发 0.12.0 稳定版后切到 `>= 0.12.0`；若上公共 opam，改用版本约束安装 |
| 2 | tag 必须先推到 GitHub，par-code 的 bump 才能进 CI | **架构正确**（顺序约束，不是选择） | 见 §1.2 结论 2。**动 `/root/dev/PAR` 需用户拍板** |
| 3 | **不**用 `register_agent_as_tool` 替换自研 `delegate` | **架构正确** | par-code 的 delegate（`lib/par_code_delegate.ml:60-140`）还做四件 SDK 原语不做的事：委派开始/工具事件/结果/错误的 UI 渲染、`finish_reason` → 用户能懂的话、失败渲染。SDK 原语只回一个 tool result，替换是 UX 回退。深度边界与取消：par-code 已用 `~cancellation_token:tok` 等价实现。**退役条件**：将来要**嵌套**委派并需要 `max_depth` 兜底时改用 SDK 原语，届时 UI 需重新设计 |
| 4 | 多模态输入不进 v0.7.5 | **范围妥协** | 编译层零影响（C8），但要有 REPL 输入通道（粘贴图片 / `@path` 语法）才叫能用，属 MINOR 的交互面新增。**退役条件**：排入 v0.8.1 候选；若 v0.8.0 上线后用户频繁要求"看这张截图改代码"，提前触发 |
| 5 | 渐进式工具加载**移出本版**，而不是"默认关闭地暴露开关" | **架构正确** | C10：当前所有工具都在 `Always` 层，开了等于没开；让它生效要先做产品决策（哪些工具可以被藏起来）+ 承担"检索失败就丢核心工具"的风险。一个死开关比没有开关更糟（用户以为开了在省 token）。**退役条件**：① 上游给出声明式分类策略（哪些内置工具 searchable），或 ② par-code 决定自定义分层并接受风险。届时重新评估放 v0.8.0 还是 v0.9.0 |
| 6 | 补 `\| Agent_tool_completed _ -> ()` 一行 | **架构正确** | 保持 match 穷举（否则 dev 下 warning、release profile 下错误），且这是纯观测事件、par-code 没有对应 UI |
| 7 | web 工具 10MB 上限作为**上游既定行为**接受，只做文档化 | **架构正确** | 报错优于静默截断；改动它属于 par-code 侧策略选择，且需要上游提供可配置阈值。**退役条件**：用户反馈大文件抓取变差 → 向上游要可配置阈值 |
| 8 | 两条必修编译点（`max_tool_schema_tokens = None`）跟着 bump 一起进 | **架构正确** | 不是可选项：不加就编译不过。两行，无行为影响（`None` = 关闭） |

## 4. 工作项

### W0 — 构建可复现化 🔴P0（前置阻塞项，需用户拍板动 PAR）

1. **把本地 PAR 的 4 个提交 + 2 个 tag 推到 GitHub**（`v0.11.0-beta.20261013`、`v0.12.0-beta.20261023`）。不做这步，W1 之后 CI 必然失败——CI 从 GitHub 取不到这两个 tag。**这一步动 `/root/dev/PAR`，par-code 无权自改。**
2. `ci.yml:29` 与 `release.yml:137` 改为带 tag 的 pin（保留现有 `rc -ne 31` 容错）：
   `opam pin add par https://github.com/jcz2020/par.git#v0.12.0-beta.20261023 -y`
3. 发布说明模板加一行"PAR SDK 版本"，让每个二进制能自证依赖版本。

**实现注记**：产物试用自证机制而非改写发布说明：`par --version` 输出 `par <ver> (built on PAR SDK v<ver>)`（v0.7.4 发布时已实测），发布说明仍由 GitHub 自动生成；CHANGES 记录地板版本。

**验收**：CI 日志里 `opam list par --installed` 打印 `0.12.0-beta.20261023`；同一 par-code tag 连续两次构建取到同一 SDK。

### W1 — SDK 地板 bump + 全量验证 🔴P0

- `dune-project` 的 `(par (>= 0.10.0))` → `(>= 0.12.0-beta.20261023)`；`dune build` 重新生成 `par_code.opam`（两处地板都要动：`dune-project:34` 与生成的 `par_code.opam:16`）。
- 本机 switch 升到该 tag（`opam pin add par /root/dev/PAR#v0.12.0-beta.20261023` + `opam upgrade par`）。
- **必修 1**：`lib/par_code_setup.ml:164-175` 的 `runtime_config` 字面量加 `max_tool_schema_tokens = None;`（对齐新地板；本版不开渐进模式，决策 5）。
- **必修 2**：`test/test_par_code_setup.ml:44-53` 同一处加同一行。
- **必修 3**：`lib/par_code_ui.ml:472-552` 的 `render_tool_event` 补 `| Agent_tool_completed _ -> ()`（决策 6）。
- `dune build` + `dune runtest` 全绿；确认没有新增 warning（尤其 release profile）。

**已知测试盲区**（不改，只记录）：`test/test_par_code_setup.ml:131-141` 断言 planner 恰好 9 个工具，工具列表是硬编码 mock → `apply_patch` 不在其中，断言仍过，但这个测试**看不见真实内置工具集的变化**。

### W2 — `apply_patch` 采纳 🟡P1

- **工具可见性**：零代码（W1 完成后自动生效）。**安全检查**：跑一次 planner 实际工具清单，确认白名单把 `apply_patch` 挡住了。
- **system prompt 指引**：默认 prompt（`lib/par_code_config.ml` 的 `default_system_prompt`）加一条"何时用 `apply_patch`（跨文件/多处改动）vs `edit`（单点精确替换）"——两个编辑工具并存而没有指引，模型会随机选。
- **文档**：`README.md` 工具表加一行；`AGENTS.md` 能力表提及；`CHANGES.md` 记"随 SDK 升级自动获得" + 已知限制（单文件写到一半崩溃不原子；同文件重叠补丁 last-writer-wins，与 `write`/`edit` 同约定）。

**验收**：真机跑一个跨两文件的改动，确认模型选择 `apply_patch` 且结果正确（dogfood，W4）。

### W3 — 行为差异文档化 🟢P1（无代码）

- CHANGES 里写清两条：① bash 输出现在完整 → doom-loop 判据更准，可能出现新的拦截（修复而非回归）；② web 工具超过 10MB 下载直接失败（原为截断）。
- README 若有 web 工具说明，补一句大小上限。

### W4 — 验证与发版 🟡P1

- 本地：全量测试 + `par ask` 真机 smoke（编辑类 1 个、问答类 1 个）。
- CI：push 后确认绿，且日志里的 PAR 版本是 tag 版本。
- dogfood：`apply_patch` 跨文件改动（模型选择 + 正确性）。
- 发版：按 `par-code-release` 技能走（版本号 bump 等用户明确指示）。

## 5. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| **PAR 的新 tag 没推到 GitHub** | W1 之后 CI 必红 | W0.1 先推（需用户拍板） |
| tag pin 后 PAR 出新 tag 要手动跟进 | SDK 更新变慢 | 有意为之。复核节奏 = 每次 par-code 发版前看一次 PAR 有无新 tag |
| beta 上游不稳定 | 偶发 SDK 回归 | 地板钉 tag + 每次发版前全量测试；出问题可回退上一个 tag |
| `apply_patch` 与 `edit` 并存导致选择混乱 | 编辑失败率上升 | W2 的 prompt 指引 + dogfood 验证 |
| bash 输出变完整后 doom-loop 更容易触发 | 之前"没输出"的循环现在会被拦 | 这是修复；写进 CHANGES 让用户知道行为变化 |
| web 工具 >10MB 直接失败 | 大文件抓取从"截断"变"报错" | 文档化；反馈多则要上游给可配置阈值 |
| 多模态推迟被感知为跟不上 | 体验缺口 | v0.8.1 候选（决策 4 已写触发条件） |
