## 0. 与既有路线图的差异（本轮修订的主因）

公开路线图早就写死了：

| 版本 | 路线图承诺 | README 能力表现状 |
|---|---|---|
| v0.10.0 | Compose mode — spec-driven orchestration with plan/execute/review/tdd/debug/verify/merge skills | `Workflows (Par.Workflow_engine)`：*State persistence registered; engine not yet invoked — roadmap v0.10.0* |

我前一版把 durable invoke 放到 v0.11、MCP 放到 v0.12，**和公开承诺冲突**。本版并回去：

- 并行归位、工作流接线、崩溃恢复 → 全部并入 **v0.10.0 Compose**（前两项是它的底座，第三项是它的可靠性前提）。
- MCP → 回到 **v0.11.0 Ecosystem**（并说明它只占该版本的第一刀）。
- LSP 留在 **v0.12.0**，与我在能力盘点里的判断一致（最该补的工具）。

| 攻击 | 修订 |
|---|---|

## 2. v0.10.0 — Compose（工作流编排 + 崩溃恢复）

公开承诺：*"Give a spec, it designs, codes, reviews, and tests end-to-end."*
内部拆四刀，按依赖排序：

### W1 并行归位（半天，纯减法）
- `delegate_batch` 改用 `Runtime.invoke_parallel`（`~parallel_limit:4 ~failure_policy:Continue_on_failure`）。
- 结果按 `spec.input` 双指针归并（`successes` / `failures` 各自保序）；纯函数 + 五种用例（全成/全败/混合/重复文案/空）。
- 删除 `lib/par_code_parallel.ml/.mli` 与 fan-out 四个用例；**保留** `delegate_batch` 入参用例（文件改名）。
- max-mode 不动（要 usage）。
- 验收：全量 28 套件；真机三路 `delegate_batch`；净减 ≥ 200 行。

### W2 工作流接线（2–3 天）
- 把 SDK 的 `register_workflow` / `submit_workflow_async` / `get_workflow_status` / `cancel_workflow` / `recover_workflow` 接进 par-code。
- 新增 REPL 命令面：`/flow run <id>`、`/flow status`、`/flow cancel`、`/flow resume`。
- 工作流定义先支持从 `.par/flows/<id>.json` 读取（与 skill 同风格：文件即配置）。
- 渲染 `Workflow_started` / `Workflow_step_completed` / `Workflow_completed` / `Workflow_orphaned`。
- 验收：单测 + 真机跑一条三段式 flow（读文件 → 摘要 → 写文件），中途 `/flow cancel` 能停、`/flow resume` 能续。

### W3 Compose 本体（8–10 天；先交最小切片）
- **先做一条三段式最小 flow**：plan → execute → review，用 `.par/flows/compose.json` 定义，端到端可跑。这一步 3 天内应有结果。
- 再补 tdd / debug / verify / merge 四个阶段 skill（plan 已有、review 由 code-reviewer 改写），完整版留到 v0.10.1。
- 与现有模块的分工：
  - `par_code_plan_tools`：提供 plan 阶段的产物，**不重写**；
  - `par_code_chain`：决定"还要不要继续"；flow 决定"下一步做什么"；
  - `par_code_goal`：目标状态不交。
- 验收：一段真实需求走完 plan → execute → review，产出可提交的改动。

### W4 崩溃恢复（1–2 天，可靠性前提）
- `Runtime.invoke ~durable:true`（id 由 SDK 铸造）；启动 `list_orphaned_invokes` 提示；`/resume` 走 `recover_invoke`。
- 语义：至少一次；等审批挂起的运行不可恢复（SDK 明确拒绝）。
- 验收：`kill -9` 真实验 + 取消后无孤儿行的反向实验。

> **为什么 W4 归在 v0.10 而不是单独一版**：工作流的 `recover_workflow` 与 agent 的 `recover_invoke` 是同一次"可恢复执行"能力的两个层；Compose 的卖点就是"端到端长跑"，跑一半崩了不能续，等于没做完。路线图的 v0.10 行不改，只是把可靠性写进验收标准。

## 3. v0.11.0 — Ecosystem（MCP 先做第一刀）

公开承诺：*"Connect any MCP server; pull skills from URLs."* 该版本原含三块：MCP（含 OAuth）、热重载、多来源 skill。建议只把**第一刀**放进 v0.11.0 的首个发布点，其余顺延：

### MCP 核心（3–4 天）
- 配置 `mcp_servers`（`Stdio_server` / `Http_server`）→ `Runtime.create ~mcp_servers ~mcp_clock`。
- 各 agent 的 `tools` 拼上 `Runtime.mcp_tool_descriptors rt`。
- `/mcp` 列 server / 状态 / 工具数；渲染 `Mcp_server_failed`、`Mcp_tool_invoked`。
- 安全：默认空列表；逐 server 显式启用；文档写明"等同安装本地程序"，不做沙箱承诺。
- 验收：自写 20 行 stdio 假 server（不依赖 node），模型调用并拿到结果。

### 顺延（v0.11.1 / v0.12 之后）
- MCP OAuth、热重载、多来源 skill（远程 URL）——都属于"生态"，各自独立成小版本。

## 4. v0.12.0 — Code intelligence（LSP）

与我在能力盘点里的结论一致：这是当前最缺的工具面。

- `lsp` 工具：诊断 / 定义 / 引用 / 调用层级；本地起 language server（OCaml → ocamllsp，其他语言按需）。
- 与 `find` / `grep` 的关系：结构性查询走 LSP，文本查询走 grep；两者都保留。
- 风险：proot 里没有 LSP server（本机就缺 `ocaml-lsp-server`），验收需要先装；拿不到就降级为"未配置时给出明确提示"。
- 验收：在本仓库上做一次"跳定义 + 查引用 + 看诊断"。

---

## 5. 顺带可做（不进主线）

- **退役 `Par_code_payload.sanitize`**：SDK 有 `Par.Conversation_repair`（`normalize_arguments` / `repair_tool_pairs` / `validate`）。崩溃恢复会大量走"修复半截对话"，两套修复逻辑并存迟早打架 —— **建议放在 W4 之前做**。
- **富内容工具结果**：`Success_content`，`read` 回图像的前提。
- **reasoning 落库**：`Reasoning_block` 带签名回放。

---

## 6. 不建议现在做

- `tool_search`（等 MCP 把工具数撑大）。
- 会话表 `/sessions`。
- 写并行 / per-child worktree（`agent_spec.workspace` 已具备，等 Compose 稳定）。
- v0.11 的 OAuth / 热重载 / 远程 skill：先把 MCP 核心跑通。

## 7. 需要用户拍板的五个问题

1. **先发 v0.9.0 吗？** 第三/四轮审意见强烈建议先发：skills/distill 已完成、28 套件绿、真机 dogfood 做过；工作区还压着并发 + SDK 两批未提交改动。不发就开 v0.10，等于三个能力叠一起。
2. **W4 并入 v0.10.0，还是单独发 v0.10.1？** 建议并入，并且 **W4 排在 W2/W3 之前** —— 它不依赖 Compose，先落地就能让现有 REPL 的长任务可靠。
3. **v0.10.0 是否只交一条三段式 flow？** 建议是；七阶段完整版留给 v0.10.1，否则这个版本做不完也验不了。
4. **`/flow` 定义放 `.par/flows/*.json` 还是先进配置？** 建议文件（`workflow_def` 本身支持 yojson，与 skill 同风格）。
5. **MCP 首刀是否只支持 stdio？** 建议 stdio 先行（proot 能验），http 随后。
